# Hongming Tan Blog

A static, component-aware Markdown publishing system for GitHub Pages. Markdown is compiled to semantic HTML first; Vite then bundles browser modules, CSS, and assets into `dist/`.

## Architecture

```text
articles/<slug>/
├── index.md
├── assets/
└── components/          # optional article-private components

components/              # public writing components
private-content/         # ignored clone of a separate private Git repository
└── articles/<slug>/     # private Markdown, assets, and local components
themes/                  # Markdown presentation and layout
core/component-api.ts    # stable author-facing component types
core/build/               # typed contracts, Markdown AST, and validation
core/client/              # shared progressive enhancement
styles/site-header.css    # shared homepage/article site chrome
tools/create-article.ts   # draft article workspace generator
tools/promote-article.ts  # explicit private-to-public copy and review gate
tools/build-content.ts    # article and metadata generator
tsconfig.json             # strict TypeScript configuration
index.html                # generated publication-style article homepage
dist/                     # generated GitHub Pages artifact
artifacts/                # ignored local archive; never shipped or synced
```

The build has two stages:

1. `tools/build-content.ts` parses Markdown, validates component/Theme compatibility, generates each article's `index.html` and static `article-entry.ts`, then rebuilds the root article homepage from the same metadata.
2. Vite follows those static module imports, rewrites asset URLs, hashes CSS/JS, and writes the deployable site to `dist/`.

No server runtime is required. Development and CI use Node.js 24 LTS; `.nvmrc`
is provided for local version managers. All first-party executable source is
TypeScript. Build-time scripts run through `tsx`, while Vite transpiles browser
modules and generated article entries for static deployment.

The root `index.html` is generated by `core/build/home.ts`; do not edit its article list by hand. Production entry points are deliberately limited to this homepage and `articles/<slug>/index.html`.

## Commands

```bash
npm install
npm run dev
npm run dev:public
npm run dev:private
npm run build
npm run preview
```

Project validation:

```bash
npm test
npm run typecheck
npm run verify
```

`npm test` runs the TypeScript project tests under `tests/`.
`npm run typecheck` checks all first-party TypeScript without emitting
JavaScript. `npm run verify` runs both, checks that generated article output is
current, and completes a production Vite build. Pull requests and GitHub Pages
deployment both use this same command; deployment only uploads `dist/` after
verification succeeds.

When the separate private repository is present, run `npm run verify:private`.
It first performs the complete public verification above, then type-checks and
renders every private article without writing private HTML to disk. The public
GitHub Actions workflow intentionally does not run this command because it has
no access to the private repository.

TypeScript covers the build system, Themes, shared and local components,
browser runtime, site Header, tests, tools, Vite configuration, and generated
article entry modules. Runtime validation of Markdown and YAML remains
authoritative; static types do not replace those checks.

The local servers have deliberately separate views and fixed ports:

| Command | Port | Homepage contents |
| --- | --- | --- |
| `npm run dev` / `npm run dev:public` | `5173` | Published articles only |
| `npm run dev:private` | `5174` | Published, draft, and private articles |
| `npm run preview` | `4173` | The final production `dist/` artifact |

Both development servers watch their article trees. Adding, deleting, renaming,
publishing, or drafting an article refreshes the appropriate page without
restarting Vite. The private server replaces `/` with a local-only homepage
generated in memory; draft and private entries receive explicit status labels.
That homepage is never written to `index.html`.

Private article previews stay in memory under
`/__private/articles/<slug>/`; production builds never read the private
repository. The fixed development ports use `strictPort`, so accidentally
starting a second copy fails clearly instead of silently moving to another
address.

### Local Component Workbench

While either development server is running, open:

```text
http://localhost:5173/__workbench/
http://localhost:5174/__workbench/
```

The Workbench discovers every registered `component.yaml` automatically. Shared
components are always available; selecting an article adds only that article's
local components and switches to its declared Theme. On port `5174` it groups
published, draft, and locked private article contexts separately. Component fields are
generated from the manifest property schema, examples provide initial values,
and the preview uses the same Markdown parser, compatibility checks, component
renderer, Theme CSS, and optional client hydration used by real articles.

Use the Theme selector to test compatible variants, edit properties and Markdown
body in place, then choose **Copy Markdown** to paste the generated directive
into an article. Unsupported Theme/capability combinations remain visible only
when **Show incompatible components** is enabled and fail with the same message
as a content build.

The Workbench is a development-server route, not a production page. Its source
is committed so every local checkout has the authoring tool, but it is not a
Vite production entry point. `npm run build:check` scans `dist/` and fails if a
Workbench route, API marker, or client asset leaks into the GitHub Pages artifact.

## Writing an article

Create a draft writing workspace by specifying a Theme:

```bash
npm run article:new -- --theme anthropic
```

This creates `articles/<slug>/index.md`, `assets/`, and `components/`. The Theme
is the only required CLI argument. The generated article defaults to today's
date and `visibility: draft`, so it does not appear on the homepage until published.
While `npm run dev:private` is running, the draft is available directly at
`/articles/<slug>/` and appears on the port `5174` local homepage. Its preview
HTML and entry module are kept in memory and are never written as publishable
article output. The public port `5173` deliberately does not expose drafts.

Common optional metadata:

```bash
npm run article:new -- \
  --theme distill \
  --title "Sparse Feature Geometry" \
  --slug sparse-feature-geometry \
  --summary "A short article summary." \
  --category Research
```

Use `--publish` to create with `visibility: public`. Run
`npm run article:new -- --help` for every supported option.

To publish an existing public-repository draft, change `visibility: draft` to
`visibility: public`. The development server then writes its article output and adds
it to the homepage automatically. Production builds always exclude drafts.

The generated `index.md` follows this structure:

```markdown
---
title: Sparse Feature Geometry
date: 2026-07-21
category: Research
summary: Optional index and page description.
author: Hongming Tan
affiliation: Independent Researcher
theme: distill
visibility: draft
---

## First section

Article content.
```

`title` and `date` are required. `category` is optional and, when present, is used
only on the homepage article list. Individual article pages never render category labels.

Article visibility has three explicit states:

| Visibility | Source repository | Local preview | Production |
| --- | --- | --- | --- |
| `public` | public site repository | `/articles/<slug>/` | homepage and `dist/` |
| `draft` | public site repository | `/articles/<slug>/` | excluded |
| `private` | private writing repository only | `/__private/articles/<slug>/` | rejected |

Legacy `draft: true` remains readable as `visibility: draft`, but new files use
the explicit visibility field.

## Private writing repository

Create a separate private GitHub repository and clone it into the ignored
`private-content/` directory:

```bash
git clone \
  git@github.com:harmonytan/harmonytan-private-writing.git \
  private-content
mkdir -p private-content/articles
```

`private-content/` is an ordinary nested clone, not a submodule. The public
repository records neither its files nor a private remote/commit pointer. Sync
the two histories independently:

```bash
git add . && git commit -m "Update public blog" && git push

git -C private-content add .
git -C private-content commit -m "Update private writing"
git -C private-content push
```

Create a private article with the same Theme, asset, component, and Markdown
structure as a public article:

```bash
npm run article:new -- \
  --theme anthropic \
  --private \
  --title "Private Research Notes"
```

The command refuses to create `private-content/` implicitly, so an ignored but
unsynchronized folder cannot be mistaken for the private Git repository.

Preview and validate the complete private collection:

```bash
npm run dev:private
npm run verify:private
```

The default private source is `private-content/articles`. Set
`BLOG_PRIVATE_ARTICLES_DIR` to override it; `.env.local` is ignored and may be
copied from `.env.example` for Vite development. CLI commands also accept the
same process environment variable.

Private articles and components use the production Markdown renderer and Theme
code, but their HTML and entry modules are kept in memory. Local assets and
client modules are served only through the development-only `__private` route.
Keep the development server on its default loopback interface; do not add
`--host 0.0.0.0` while viewing confidential material.

When an article is ready to leave the private repository, promote it explicitly:

```bash
npm run article:promote -- --slug private-research-notes
```

Promotion defaults to a reviewable public-repository draft. Add `--publish` only
for intentional immediate publication. The command preserves the private
source, rejects generated files, symbolic links, missing local assets, and
privacy markers, copies through a staging directory, renders the result, and
never commits automatically. `--allow-warnings` is available only after manually
reviewing reported markers.

Asset paths are local to the article:

```markdown
![Figure title | A descriptive caption.](./assets/figure.svg){wide}
```

Supported figure modifiers are `{wide}`, `{full}`, and percentage widths such as `{70%}`.

Current Themes:

- `distill`: Transformer Circuits-inspired research layout with a left-aligned research title, compact citations, and structured end matter. It does not render a table of contents.
- `anthropic`: Anthropic engineering-inspired editorial layout with a geometric hero, warm paper palette, sans-serif display typography, and a 640px serif reading column.

Each Theme manifest declares its capabilities in `themes/<theme>/theme.yaml`. The content build rejects a component whose requirements are not provided by the selected Theme. `distill` remains the default when front matter does not specify a Theme.

## Components

Use a public component:

```markdown
:::component{name="shared.callout" title="Observation" tone="claim"}
The body remains ordinary Markdown.
:::
```

Use an article-private component:

```markdown
:::component{name="local.my-figure" source="./assets/data.json"}
Optional Markdown body.
:::
```

Every component must contain:

```text
component-name/
├── component.yaml       # name, scope, capabilities, Theme restrictions
├── index.ts             # build-time render() export
├── README.md            # authoring documentation
├── style.css            # optional
├── client.ts            # optional hydrate() export
└── examples/            # recommended Markdown fixtures
```

Browser code must use ESM TypeScript. The generated `article-entry.ts` contains static imports so Vite can bundle private modules correctly for GitHub Pages. Do not construct production module URLs from arbitrary Markdown strings.

Component build modules import author-facing types through the stable alias,
which works at any public or private article depth:

```ts
import type {
  ComponentContextWithEscape,
} from "@blog/component-api";
```

Do not import from `core/build` with a relative path. `npm run
typecheck:private` loads `tsconfig.private.json` and adds the configured private
article tree, including when `BLOG_PRIVATE_ARTICLES_DIR` points outside this
repository.

Component manifests use a versioned, build-validated property contract:

```yaml
apiVersion: 1
name: callout
scope: shared
description: A semantic article callout.
requires: []
themes:
  only:
    - distill
    - anthropic
props:
  title:
    type: string
    default: Note
    maxLength: 120
  tone:
    type: enum
    values:
      - note
      - caution
      - claim
    default: note
  size:
    type: enum
    values:
      - compact
      - normal
      - prominent
    default: normal
```

Supported property types are `string`, `enum`, `boolean`, `number`, `integer`,
and `url`. Directive attributes are normalized to those types before
`render()` is called. Defaults are applied centrally; unknown properties,
invalid values, out-of-range numbers, and unsupported Theme combinations stop
the build with a component-specific error.

Prefer semantic variants such as `size="compact"` or `tone="claim"` over raw
CSS values. Components should emit stable `data-*` attributes and allow each
Theme to map those states to its own typography and spacing.

Basic types belong in `component.yaml`. A component with relationships between
properties may optionally export `validate({ props, content, article, theme })`
from `index.ts`; it should throw a descriptive error for an invalid
combination. `render()` always receives the normalized property object.

## Footnotes, references, math, and code

Footnotes use standard Markdown:

```markdown
The convention varies by market.[^efp]

[^efp]: This article uses futures minus physical spot.
```

Numbered references retain the existing writing syntax:

```markdown
This sentence cites a source [1].

[1]: Author, Title, Year. https://example.com/source
```

Grouped citations are also supported: `[1, 2]`. Hovering or focusing a citation shows a compact source preview.

Use numbered references for evidence, claims, reports, papers, videos, and other source material. This keeps prose as ordinary text and places a compact citation marker after the claim:

```markdown
The measured ratio continued to fall [1].

[1]: Dataset or report title. https://example.com/source
```

Reserve ordinary Markdown links such as `[Open the notebook](https://example.com/notebook)` for destinations the reader is intentionally expected to open: notebooks, repositories, tools, downloads, and navigation. The Distill Theme renders these direct links as subdued text with a thin underline rather than citation blue.

End-matter headings use ordinary Markdown. `Appendix`, `Acknowledgements`, `Acknowledgments`, `Author Contributions`, and an optional custom `Citation Information` section are moved to the shaded end-matter grid. Standard Markdown footnotes and numbered references follow automatically. `Discussion`, `Comments`, and `Replications` stay in the main reading flow; use `shared.comment` for a styled response block (see `components/comment/README.md`).

The generated citation can be overridden in front matter:

```yaml
citation:
  author: Hongming Tan
  venue: Hongming Tan
  url: https://harmonytan.github.io/articles/example/
  key: tan2026example
```

Math supports `$...$`, `$$...$$`, `\(...\)`, and `\[...\]`. KaTeX renders it during the content build, so formulas remain visible without article JavaScript.

## Deployment

The GitHub Pages workflow installs locked dependencies, builds `dist/`, and uploads that directory as the Pages artifact. Vite uses relative asset URLs (`base: "./"`), so nested article routes work both on user Pages and project Pages paths.

The old runtime and retired redirect shells are kept only in `artifacts/`. That
directory is an ignored local quarantine, not synchronized writing storage.
Private writing belongs in the independent `private-content` Git repository.
Production verification rejects Workbench routes, private preview routes, and
private-content markers in `dist/`.
